# Arquitetura do Design System

O `@bytebank/design-system` segue o **Atomic Design** (Brad Frost): a interface é montada de baixo para cima, das peças indivisíveis até as telas. Uma camada nunca importa outra acima dela, então fica explícito o que depende do quê.

Templates e páginas ficam fora do DS de propósito: eles conhecem rotas, sessão e dados (TanStack Query, Redux), e o DS é agnóstico a isso. Os hooks utilitários de interface (`src/hooks/`, por exemplo `useFocusTrap`) podem ser usados por qualquer camada.

## Regras de dependência

- **Átomo** não importa molécula nem organismo.
- **Molécula** importa átomos e outras moléculas; não importa organismo.
- **Organismo** importa átomos, moléculas e outros organismos.

As regras valem no lint (`no-restricted-imports`, definido em `eslint.layers.mjs`), tanto no `npm run lint` do pacote quanto no pre-commit. Um import "para cima" faz o lint falhar com a mensagem `Atomic Design: ...`.

Consumidores externos continuam importando tudo do barrel, sem saber a camada:

```ts
import { Button, FormField, Modal } from '@bytebank/design-system';
```

## Tokens

Os tokens vivem em `src/styles/tokens.css`, dentro do bloco `@theme` do Tailwind CSS v4: cores (marca, superfície, conteúdo, feedback, foco), tipografia, espaçamentos, raios e sombras. O `@theme` transforma cada variável em utilitário (`--color-brand-primary` vira `bg-brand-primary`, `text-brand-primary` etc.). A referência visual está em **Foundations**.

Para o Bytebank, o fator decisivo é o ambiente: Next.js com SSR e microfrontends federados. CSS estático sem runtime evita custo no servidor e no cliente, e um único `globals.css` compartilhado mantém shell e MFEs com o mesmo visual, sem duplicar estilos por componente. Padrões tipográficos recorrentes ficam como classes semânticas em `@layer components` (`src/styles/globals.css`).
